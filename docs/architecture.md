# 架构说明

## 结论

当前架构不需要整体重构。Monorepo、独立交付和服务内分层仍适合现阶段；需要补强的是平台治理与生产基础设施。采用渐进式改造，避免在业务规模尚小时引入服务发现、分布式事务和独立 IAM 的运维成本。

## 逻辑结构

```text
浏览器 / 门店展示屏
        |
  API Gateway（待完善：路由、统一认证、限流、请求 ID）
        |
        +-- property_verification
        |
        +-- store_media ---- SQLite / 本地媒体（当前单实例）
                 |
                 +-- PostgreSQL / 对象存储（规模化目标）
```

服务内部使用以下依赖方向：

```text
api -> application -> domain <- infrastructure
```

- `api`：HTTP 协议、输入输出与认证依赖；
- `application`：用例编排和事务边界；
- `domain`：实体与业务授权规则，不依赖 Web 或数据库框架；
- `infrastructure`：数据库、文件、外部 HTTP、队列和配置适配；
- `security`：密码、令牌、上传校验等纯安全能力。

简单 CRUD 服务不必机械创建空目录；只有存在明确领域规则或可替换适配器时才增加抽象。

## 强制边界

1. 服务不能直接 import 另一个服务的内部模块，也不能查询对方数据库或文件目录。
2. 跨服务共享仅允许无业务含义的 `packages/`、版本化 HTTP API 或 `shared_contracts` 中的事件结构。
3. 网关处理通用入口能力；“某区域经理能否发布某门店内容”等业务授权必须由业务服务再次校验。
4. 每个服务在 `services/catalog.yaml` 登记所有者、健康检查、配置前缀、数据所有权与依赖。
5. 配置仅从环境变量或密钥管理系统注入，真实凭据不进入仓库。

## `store_media` 当前边界

该服务拥有门店、用户、角色、会话、媒体元数据和媒体文件。角色包括系统管理员、区域经理、店长和店员；授权按区域和门店范围执行。

本地身份是过渡方案。第二个业务服务需要登录、需要统一登出或企业 SSO 时，应提取 `identity_access`：身份服务负责认证和粗粒度角色声明，各业务服务继续负责资源级授权。禁止直接复用或复制 `store_media` 的用户表。

## 生产化缺口与优先级

| 优先级 | 改造 | 触发条件 |
| --- | --- | --- |
| P0 | 网关、TLS、可信代理头、密钥管理、备份、上传病毒扫描 | 对内部用户正式开放前 |
| P0 | PostgreSQL + 对象存储 + 数据迁移 | 多实例或媒体数据不可丢失时 |
| P1 | 统一身份/SSO、短期访问令牌、密钥轮换 | 第二个受保护服务前 |
| P1 | 结构化日志、指标、链路追踪、告警 | 进入稳定运营期 |
| P1 | 视频异步转码、缩略图和内容审核 | 视频格式或吞吐增加时 |
| P2 | 服务发现与事件总线 | 动态实例和异步集成明显增加时 |

具体决策与阶段计划见 [ADR-0001](adr/0001-evolutionary-platform-architecture.md)。
